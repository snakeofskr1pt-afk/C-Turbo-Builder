# cpp-turbo-builder

Кеш-проксі + оркестратор Unity Build для C++ — **один бінарник, нуль залежностей, збирається офлайн**.

Ідея проста: C++ збирається повільно не через сам компілятор, а через те, що мільйон рядків
заголовків перепарсюються з нуля для кожного `.cpp`. `turbo` робить дві речі:

1. **Кеш-проксі** — хешує флаги, компілятор і вміст `.cpp` разом з **усіма** залежними
   заголовками; якщо такий об'єктний файл уже збирався — копіює його з кешу, не запускаючи
   компілятор.
2. **Unity Build** — склеює по 8–10 `.cpp` в один чанк і компілює чанки паралельно по кількості
   ядер, після чого лінкує фінальний `.exe`.
3. **`turbo.json`** — налаштування проєкту: компілятор, `-I`/`-D`, виключення, розмір чанку,
   кількість потоків, лінкер. Заголовки хешуються паралельно на всіх ядрах.

```
             turbo build -- g++ -Iinclude -O2
                        │
        ┌───────────────┴────────────────┐
        │  1. знайти всі .cpp            │
        │  2. склеїти в .build/unity_N   │  ← спільні заголовки парсяться раз на чанк
        │  3. N потоків → кеш-проксі     │
        │       ├─ HIT  → копія .obj     │
        │       └─ MISS → компілятор     │
        │  4. лінкування → app.exe       │
        └────────────────────────────────┘
```

## Швидкий старт

Потрібен лише Rust (1.70+). Мережа не потрібна: залежностей немає взагалі.

```powershell
cargo build --release --offline
# бінарники: target\release\turbo.exe (+ mockcc.exe — тестовий фейковий компілятор)

# Варіант 1: усе з turbo.json (у прикладі вже є — компілятор, -I, чанк, out)
target\release\turbo.exe build --root examples\cpp_demo

# Варіант 2: усе прапорцями командного рядка
target\release\turbo.exe build --root examples\cpp_demo --jobs 8 --chunk-size 4 -- g++ -Iexamples\cpp_demo\include -O2
```

Другий запуск тієї ж команди майже нічого не компілює — усе береться з кешу.

### Як підключити до наявного білда (MSVC / CMake / make)

`turbo fastcache` — це drop-in проксі з тим самим синтаксисом, що й компілятор:

```powershell
# MSVC
target\release\turbo.exe fastcache -- cl.exe /c src\a.cpp /Fo:build\a.obj /Iinclude
# GCC / Clang
target\release\turbo.exe fastcache -- g++ -c src/a.cpp -o build/a.o -Iinclude
```

У CMake це підключається як компілятор-обгортка (`CMAKE_CXX_COMPILER_LAUNCHER`), у make — як
`CXX := turbo fastcache -- g++`.

## Команди

| Команда | Що робить |
|---|---|
| `turbo fastcache [--cache-dir DIR] [-v] -- <компілятор> <флаги>` | Кеш-проксі для одного юніта |
| `turbo build [--root DIR] [--jobs N] [--chunk-size N] [--out FILE] [--linker PATH] [--config FILE] [--no-config] [--cache-dir DIR] [--quiet] [-- <компілятор> <флаги>]` | Пошук джерел, Unity Build, паралельна збірка, лінк. Без `--` компілятор і флаги беруться з `turbo.json` |
| `turbo hash [--manifest] -- <компілятор> <флаги>` | Показати ключ кешу і які файли в нього входять |
| `turbo cache dir\|stats\|clear [--cache-dir DIR]` | Керування кешем |

Приклади:

```powershell
turbo build --root . --jobs 16 --chunk-size 10 --out game.exe -- cl /O2 /Iinclude
turbo build --root . --out app -- g++ -Iinclude -std=c++20 -O2
turbo build --root examples\cpp_demo                            # усе з turbo.json
turbo build --root . --config build\turbo-release.json          # інший конфіг
turbo build --root . --linker lld-link.exe -- cl /O2            # явний лінкер
turbo hash --manifest -- g++ -c src/a.cpp -o a.o -Iinclude      # чому кеш промахнувся
```

Змінні середовища:

| Змінна | Призначення |
|---|---|
| `TURBO_CACHE_DIR` | тека кешу (типово `%LOCALAPPDATA%\cpp-turbo-cache`) |
| `TURBO_JOBS` | типова кількість воркерів (і потоків хешування заголовків) |
| `TURBO_VERBOSE=1` | докладний лог |
| `TURBO_EXTRA_KEY` | додаткова сіль у кожному ключі (якщо білд залежить від env) |

Коди виходу: `0` — успіх, `2` — помилка самого інструмента, інші — код компілятора/лінкера.

## `turbo.json`

Файл у корені проєкту (або `--config FILE`; `--no-config` його ігнорує). Пріоритет:
**командний рядок → `turbo.json` → вбудовані значення**.

```json
{
  "compiler": "g++",
  "flags": ["-O2", "-std=c++20"],
  "include": ["include", "third_party/include"],
  "defines": { "NDEBUG": null, "ENGINE_VERSION": "42" },
  "exclude": ["third_party", "tests"],
  "chunkSize": 10,
  "jobs": 8,
  "out": "app.exe",
  "linker": "lld-link.exe",
  "linkFlags": ["-lm"]
}
```

| Ключ | Тип | Значення |
|---|---|---|
| `compiler` | string | компілятор (`g++`, `cl.exe`, `C:\LLVM\bin\clang++.exe`) |
| `flags` | string[] | сирі флаги компіляції, передаються як є |
| `include` | string[] | теки `-I`/`/I`; відносні шляхи рахуються від теки `turbo.json` |
| `defines` | object | `-D`/`/D`: `null` → голий `NAME`, `"42"` → `NAME=42`, `true/false` → `1`/`0` |
| `exclude` | string[] | теки, які не сканувати (додатково до `.git`, `build`, `target`, `third_party`…) |
| `chunkSize` | number | скільки `.cpp` в один Unity-чанк |
| `jobs` | number | кількість паралельних компіляцій |
| `out` | string | ім'я/шлях фінального `.exe` |
| `linker` | string | явний лінкер (`link.exe`, `lld-link.exe`, `g++`…) |
| `linkFlags` | string[] | флаги **тільки** для лінкування (`-lm`, `/LIBPATH:…`) |

- Компілятор для `include`/`defines` визначається за назвою: `cl`/`clang-cl`/`link` — MSVC-синтаксис,
  решта — GCC-синтаксис.
- Невідомі ключі не ламають білд — друкується попередження.
- JSON парситься власним читачем (без serde), з коректними помилками: файл, рядок/зміщення.

## Як влаштований кеш

Ключ = `SHA-256` від канонічного маніфесту:

```
cpp-turbo-builder cache-key v1
compiler   cl.exe <size> <mtime>          ← оновлення компілятора скидає кеш
toolchain  msvc
flag       /O2
flag       /Iinclude
file       c:/proj/src/a.cpp   <sha256>
file       c:/proj/include/a.h <sha256>   ← і так рекурсивно по всіх #include "..."
```

- Кеш лежить у `%LOCALAPPDATA%\cpp-turbo-cache\<ключ>.obj` (+ `<ключ>.meta` з маніфестом —
  щоб через місяць було видно, **чому** був хіт або промах).
- Запис атомарний: тимчасовий файл + `rename`, тож паралельні воркери не бачать «половину» об'єкта.
- **Невдалі компіляції не кешуються** — наступний запуск знову покличе компілятор.
- Заголовки шукаються як компілятор: `"..."` — спершу відносно файлу, потім у `-I`; `<...>` — лише
  в `-I`. Системні заголовки (`<vector>`) не хешуються: їх «пінить» ідентичність компілятора + флаги.
- Парсер `#include` навмисно наївний (сканує байти). Це **безпечно**: зайвий файл у ключі дає
  зайвий промах, але не дає хибного хіта. Хибний хіт — це псування, хибний промах — лише повільніше.
- Хешування заголовків **паралельне**: перший прохід читає файли, щоб знайти `#include`, другий —
  рахує SHA-256 на всіх ядрах (стільки потоків, скільки `TURBO_JOBS`/ядер). Порядок файлів у ключі
  сортований, тому результат детермінований незалежно від планування потоків.

## Що вже працює (і що ні)

| Етап оригінального плану | Стан |
|---|---|
| 1. Кеш-проксі (BLAKE3, `std::process::Command`) | ✅ `turbo fastcache`. Замість BLAKE3 — власний SHA-256 (чому — нижче) |
| 2. Оркестратор + Unity Build + worker pool + лінк | ✅ `turbo build` — але на Rust, а не на Go (чому — нижче) |
| 3.1 Рекурсивний парсер `#include` з паралельним хешуванням | ✅ рекурсія + паралельне хешування на std-потоках |
| 3.2 `turbo.json` (шляхи заголовків, макроси, чанк, компілятор) | ✅ `turbo.json` з власним JSON-парсером |
| 4. Заміри `Measure-Command` | ✅ `scripts\bench.ps1` + цифри нижче |

### Чому Rust, а не Rust + Go

Оригінальний план: проксі на Rust, оркестратор на Go. На машині розробки **Go не встановлений і
мережі немає** (TLS блокується), тому Go-частину неможливо було б навіть скомпілювати, а тим паче
протестувати. Тому оркестратор — той самий бінарник `turbo`, окрема підкоманда.

Контракт при цьому не постраждав: `fastcache` — самостійний drop-in проксі, який будь-який
оркестратор (на Go, Python, CMake) викликає як звичайний компілятор. Тобто Етап 1 можна
використовувати окремо, а Go-версію Етапу 2 дописати пізніше без переробки ядра.

### Чому SHA-256, а не BLAKE3

`blake3` — це крейт з crates.io. Немає мережі → немає залежностей. SHA-256 реалізований вручну
(~120 рядків, перевірений на офіційних тест-векторах, включно з мільйоном символів `a`). Швидкості
вистачає з головою: хешування десятків заголовків — одиниці мілісекунд проти сотень мілісекунд
компіляції. Замінити на BLAKE3 можна, не чіпаючи решти коду: API `hash_bytes` / `hash_reader`.

## Тести

```powershell
cargo test --offline
```

57 тестів: 45 юніт- (SHA-256, парсер `#include`, паралельне хешування, JSON-парсер і `turbo.json`,
ключі кешу, чанкування, шляхи) і 12 інтеграційних, які ганяють real CLI end-to-end:

- холодна збірка → рівно стільки запусків компілятора, скільки чанків;
- гаряча збірка → **нуль** запусків компілятора;
- правка заголовка → інвалідуються лише чанки, що його включають;
- правка невикористовуваного заголовка → кеш не скидається;
- зміна флага → скидається все;
- помилка компіляції → код виходу прокидається і **не кешується**;
- паралельна збірка 6 чанків у 4 потоки → один `exe`;
- `turbo.json` керує компілятором, `-I`/`-D`, виключеннями, чанком і `out`; CLI має приоритет;
- битий `turbo.json` → зрозуміла помилка з назвою файлу, код виходу 2;
- `cache stats/clear`, `hash`, `--help`, коди виходу.

Тести не потребують MSVC/GCC: замість компілятора використовується `mockcc` — маленький фейковий
компілятор/лінкер із цього ж пакета. Він справді розгортає ланцюжок `#include`, тому інвалідація
заголовків перевіряється чесно.

## Заміри

`mockcc` — це не реальний C++ компілятор, тому цифри нижче показують **накладні витрати самого
інструмента**, а не виграш на «важкому» C++. Проєкт `examples/cpp_demo` (3 `.cpp`, 2 заголовки,
2 чанки, 4 потоки):

| Сценарій | Час |
|---|---|
| Холодна збірка (кеш порожній) | 79–125 мс (перший прогрів — до 200 мс) |
| Гаряча збірка (усе з кешу) | 44–64 мс |
| Один хіт проксі (окремий юніт) | ~11 мс |
| Прискорення на гарячому шляху | ~1.7–2.2× |

Тобто на гарячому шляху залишається лише: переписати `.build/unity_*.cpp`, перехешувати
заголовки, скопіювати `.obj` і злінкувати.

Окремо — **паралельне хешування** (`turbo hash` на синтетичних проєктах, 4 логічні ядра,
медіана з 6 запусків):

| Корпус | 1 потік | 4 потоки | 8 потоків | 16 потоків |
|---|---|---|---|---|
| 200 заголовків / 1.7 МБ | 160 мс | **82 мс** | 85 мс | 82 мс |
| 400 заголовків / 27 МБ | 469 мс | **276 мс** | 297 мс | 283 мс |

Виграш ~1.7–2× уже на 4 ядрах; більше потоків тут не додають, бо це I/O + скалярний SHA-256,
а не чиста арифметика. Для маленьких графів (< 8 файлів або < 1 МБ) хешування лишається
послідовним, щоб не платити за створення потоків.

Замірити на своєму проєкті з реальним компілятором:

```powershell
.\scripts\bench.ps1 -Root C:\path\to\project -Compiler g++ -Jobs 16 -ChunkSize 8
# якщо PowerShell блокує локальні скрипти:
powershell -ExecutionPolicy Bypass -File .\scripts\bench.ps1 -Root . -Compiler g++ -Jobs 16 -ChunkSize 8
```

## Відомі обмеження

- **Не перевірено на реальному MSVC/GCC** у цьому середовищі: компілятора немає (VS Build Tools
  не встановлені). Логіка побудови командних рядків покрита юніт-тестами, end-to-end — через `mockcc`.
- Системні заголовки (`<...>`, не знайдені в `-I`) не хешуються — оновлення SDK їх не інвалідує.
  Ідентичність компілятора (розмір+mtime) частково це покриває.
- Наївний парсер `#include` не розуміє макросів, що генерують `#include`, і PCH.
- Два паралельні промахи на той самий ключ можуть скомпілювати двічі (результат коректний,
  просто зайва робота). Хіти/записи від цього не ламаються завдяки атомарному запису.
- Два проходи по файлах під час хешування (перший — пошук `#include`, другий — паралельний SHA-256):
  на холодному диску це подвійне читання, але воно йде з page-cache ОС і розпаралелене.
- `turbo.json` не підтримує коментарі (це чистий JSON) і не має `$schema`-валідації.

## Roadmap

1. Підтримка PCH і `/FI`-макросів; докачування ключа при зміні системних заголовків (SDK-версія).
2. Блокування ключа (lock-файл), щоб паралельні промахи не дублювали компіляцію.
3. Прогін CI з реальним компілятором (MSVC на Windows, GCC/Clang на Linux) — workflow уже в репо.
4. Опційний бекенд BLAKE3 за фічею, коли буде мережа.
5. `turbo.json`: профілі (`build`, `release`) і наслідування конфігів.
