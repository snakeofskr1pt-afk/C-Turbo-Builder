# Дизайн-рішення та інваріанти

Короткий документ для тих, хто читатиме код: **чому** зроблено так, і які властивості
гарантуються. README описує «що і як користуватись», тут — «чому саме так».

## 1. Головний інваріант: хибний промах — можна, хибний хіт — ніколи

Кеш повертає об'єктний файл без запуску компілятора. Отже будь-яка помилка в ключі, яка призводить
до хіта при зміненому вході, — це тихо зламаний білд. Тому всі рішення зсунуті в безпечний бік:

- Парсер `#include` сканує **сирі байти** без лексера. Закоментований `#include` або рядок у
  лапках теж потрапляє в залежності → зайвий промах. Це прийнятно.
- Якщо заголовок не знайдено (`<vector>`), він не входить у ключ. Це єдине місце, де можливий
  «недолік» входу; його компенсують ідентичність компілятора (розмір + mtime бінарника) і прапорці.
- Ліміти обходу (глибина 64, файл 32 МБ) не обрізають ключ мовчки: `CacheKey::truncated`
  піднімає прапорець, а `turbo fastcache` друкує попередження.
- Помилка компіляції — це `Outcome::Failed(code)`, а не `Ok`: нічого не записується в кеш.
- Порожній (0 байт) файл кешу вважається непридатним. Запис і копіювання атомарні
  (temp + rename), тому «половина об'єкта» не може стати кеш-записом.

## 2. Ключ — не хеш «вихідного файлу», а маніфест

`cachekey.rs` будує текстовий маніфест і хешує його. Чому не просто «скомбінувати хеші»:

- Маніфест **читабельний** і зберігається поруч з об'єктом (`<ключ>.meta`). Через місяць
  `cat cache/<ключ>.meta` відповідає на питання «чому цей хіт», не вимагаючи нічого запускати.
- Порядок не впливає: файли сортуються за нормалізованим ключем шляху.
- Явні мітки (`compiler`, `flag`, `file`, `salt`) унеможливлюють «склеювання» різних сутностей
  в один рядок (наприклад, прапор із табуляцією).
- Прапорці зберігаються **в оригінальному порядку**: для MSVC порядок `-I` має значення.
- Шлях нормалізується: абсолютний, `/`-роздільники, нижній регістр на Windows — щоб `src\a.cpp`
  і `src/a.cpp` давали один ключ.

Компілятор у ключі — це `ім'я + розмір + mtime`, а не повний шлях. Компроміс: перенесення
toolchain'у в іншу теку не скидає кеш, а оновлення/переустановка — скидає.

## 3. Unity Build: чому 8–10 файлів і чому `#include "../src/a.cpp"`

- Один чанк = один запуск компілятора = один заголовок парситься один раз на чанк. Замало файлів
  у чанку — ефекту немає; забагато — кожна правка інвалідує величезний юніт і росте пам'ять.
  8–10 — розумний компроміс (прапорець `--chunk-size`).
- Юніт-файли лежать у `.build/`, тому шляхи в `#include` — відносні (`../src/a.cpp`). Це робить
  `.build/unity_N.cpp` переносимими між машинами й читабельними при дебазі.
- `.build` перегенеровується щозапуску: застарілі чанки не можуть потрапити в лінк.
- Символьні посилання при скануванні не розгортаються — захист від циклів і дублікатів.
- Теки `.git`, `target`, `build`, `third_party`, `vendor` тощо пропускаються, щоб не збирати
  чужі джерела (список у `orchestrator.rs`).

## 4. Паралельність: `thread::scope` + атомарний курсор

Замість каналів — `scoped threads` (std, без `rayon`/`crossbeam`) і `AtomicUsize` як курсор:

- Немає черги, яку треба закривати й синхронізувати: просто «хто взяв наступний індекс».
- Результати складаються в `Mutex<Vec<Option<...>>>` за індексом; порядок звіту детермінований.
- Помилка інфраструктури (IO, не запускається компілятор) обирається за найменшим індексом,
  щоб повідомлення було стабільним між запусками.
- Один спільний кеш на всі потоки — це безпечно: читання/копіювання атомарне, запис атомарний,
  дублікат роботи можливий лише для однакових ключів (документоване обмеження).

## 4a. Паралельне хешування заголовків

Знайти `#include` без читання файлу неможливо, тому обхід графа неминуче читає файли. Дизайн:

1. **Прохід 1 (послідовний)**: обхід графа `#include`, читання кожного файлу лише заради пошуку
   директив. Результат — множина шляхів + список нерозв'язаних include'ів.
2. **Прохід 2 (паралельний)**: множина шляхів ріжеться на `jobs` неперервних діапазонів,
   кожен потік рахує SHA-256 своїх файлів. Потоки створюються `thread::scope`, тож позичати
   `&[PathBuf]` можна без `Arc`.
3. Результати склеюються у вихідному порядку, потім файли **сортуються за ключем шляху** — тому
   ключ не залежить від того, як ОС розклала потоки.

Друге читання майже безкоштовне: сторінки вже в page cache ОС, а на Windows основний час іде не
в SHA-256, а в `open`/`read` на кожен файл — саме це й перекривається потоками. Для маленьких
графів (< 8 файлів або < 1 МБ сумарно) хешування лишається послідовним, щоб не платити за
створення потоків.

Замір на 4 логічних ядрах (медіана з 6 запусків `turbo hash`): 200 заголовків / 1.7 МБ —
160 мс → 82 мс; 400 заголовків / 27 МБ — 469 мс → 276 мс. Більше 4 потоків не додають:
вузьке місце — I/O і скалярний SHA-256, а не CPU.

## 4b. `turbo.json`: власний JSON-парсер і пріоритети

Serde недоступний офлайн, тому в `config.rs` — рекурсивний спуск на ~250 рядків: об'єкти, масиви,
рядки (з `\uXXXX` і surrogate pairs), числа, `true/false/null`, коректні помилки зі зміщенням у
байтах. Він реалізує повну граматику RFC 8259, включно з забороною ведучих нулів (`01` — помилка).

Пріоритет: **CLI → `turbo.json` → дефолти**. Практичні наслідки:

- `compiler`/`flags` можуть жити в конфізі, але `-- g++ -O3` їх перекриє для конкретного запуску.
- `include` з конфіга розв'язується **відносно теки конфіга**, а не `cwd`, і стає абсолютним
  `-I`-флагом — тому `turbo build --root інша/тека` не ламає шляхи.
- Ключ кешу не знає про `turbo.json` напряму: він бачить лише **ефективні флаги**, які з нього
  вийшли. Це навмисно — інакше будь-яка косметична правка конфіга скидала б весь кеш.

## 5. Діагностика замість «мовчазних» хітів

- `turbo hash --manifest` — друкує маніфест і кількість файлів. Це головний інструмент, коли
  «чому воно не кешується».
- `turbo build -v` — по кожному юніту: `HIT`/`MISS`/`FAIL`, час, кількість файлів у ключі;
  плюс рядок `[turbo] config: <шлях>`, якщо конфіг підхопився.
- Підсумок: `N chunk(s): X cache hit(s), Y miss(es) in T s`.
- `turbo cache stats` — скільки об'єктів і скільки місця.

## 6. Чому саме такий стек

- **Один бінарник `turbo`** (підкоманди `fastcache`/`build`): Go на машині не було й поставити його
  було нізвідки (нема мережі). Компроміс без втрати архітектури: `fastcache` — стабільний
  drop-in-контракт, який може викликати будь-який зовнішній оркестратор.
- **Нуль залежностей**: офлайн-збірка, відсутність supply-chain ризику, `cargo build` працює
  навіть без crates.io.
- **SHA-256 вручну**: BLAKE3 — крейт, недоступний офлайн. SHA-256 швидший за компіляцію на
  порядки, тож вузьким місцем не стає.
- **`mockcc` у репозиторії**: дає змогу перевіряти логіку кешу й паралельності в CI та на
  машинах без C++ тулчейну (як ця). Це тестовий інструмент, не частина продакшн-збірки.

## 7. Чого свідомо немає

- PCH, макрос-залежності, генерація `#include` кодом — потребує справжнього препроцесора
  (можна пізніше через `-M`/`/showIncludes` від компілятора).
- Мережевого/спільного кешу — ключ містить абсолютні шляхи, тож між машинами кеш не переноситься.
- Демона/сервера — процес-на-юніт достатньо швидкий, а складність (життєвий цикл, IPC,
  інвалідація) не виправдана до перших реальних замірів на важкому C++.
